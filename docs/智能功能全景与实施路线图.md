## 1. 目标、依据与时间预算

产品目标：用户说出银行业务目标，VeraLane 能澄清缺失信息、查询证据、编排步骤、取得具体授权、执行模拟操作，并提供可以核对的结果。

本次核查的[大赛官网](https://fintechathon.g-ican.com/)说明：国内人工智能赛道至少覆盖六类核心场景中的三类，鼓励覆盖全部；作品提交截止为 2026-11-02。具体提交时刻和格式继续以报名后台为准。技术文档、安全自评、源码与部署材料、10 分钟以内答辩 PPT 和 5 分钟以内视频，按用户已确认的提交要求准备。

当前资源：一名主要开发者每周约 10 小时，Codex 在本地协助开发，DeepSeek 总预算约 20 元。10 月 3 日至 11 月 2 日约有 43 小时个人投入量，规划使用约 40 小时，保留余量。工时是排期参考，包含选择、试用、验收、录制和提交，不是全部功能能如期完成的保证。

优先级定义：

- **已完成**：有可运行流程及现有测试证据。
- **P0 / 参赛主交付**：深化转账、账单、订阅三条主线，加一个基于现有工具的跨场景闭环及共用执行控制。
- **P1 / 有余量扩展**：卡片最小闭环、生日资金计划；独立估时，通过依赖验收后再安排。
- **P2 / 完整产品规划**：理财交易、完整卡申请/提额、周期转账等；不计入当前约 40 小时的主交付承诺。

## 3. 六类智能功能完整清单

### A. 智能转账与 AA

| 功能 | 用户表达与智能行为 | 优先级 / 边界 |
| --- | --- | --- |
| 一句话转账、预约、AA | 提取对象、金额、用途与时间；缺失则补问，同名则选择；展示计划和回执 | 已完成；继续回归验证 |
| 关系与备注别名 | “房东是林悦，以后房租转给她”；用户确认保存别名，“给房东转房租”时解析到明确联系人 | P1；金额缺失仍补问，多个匹配仍澄清；不能根据一条历史备注自行认定关系 |
| 相似付款提醒 | “刚刚是否转过这笔？”；检查同一收款人、金额和近期记录，展示疑似重复交易 | P1；业务重复提醒与接口幂等分开，合法重复付款仍可再次明确确认 |
| 周期转账 | “每月 5 日转 300 元，连续三个月”；展开未来执行日期、总次数、单笔及累计上限 | P2；独立长期授权；无对应日期、余额不足等先约定处理，不默认无限循环或补扣 |
| 批量转账 | 一句话给多位联系人付款，逐行核对，记录每笔结果 | P2；逐笔幂等、部分失败如实报告，不自动撤销已完成转账 |
| AA 扩展 | 多人垫付抵消、按比例分摊、人工按菜品拆账、小票 OCR、分次付款、退款、催收 | 比例、分次回款、退款、保存净额计划及本人相关逐笔模拟、人工按菜品拆分、本机 OCR 草稿识别已实现；外部催收未实现 |

### B. 智能账单洞察

**下一项建议开发的功能：智能账单问答与消费变化解释。**

| 功能 | 用户表达与智能行为 | 优先级 / 验收重点 |
| --- | --- | --- |
| 自然语言查账 | “上个月餐饮花了多少”“找出超过 200 元的消费”；生成受限查询条件 | P0；日期、分类、金额条件可见，结果能逐笔复算 |
| 支出变化解释 | “本月为什么比上月花得多”；按分类和商户计算增减，再生成解释 | P0；比较同长度期间或完整月份；基期为 0 不输出虚假的增长百分比 |
| 异常线索调查 | 检查相似重复扣费、同商户金额突增、已知订阅涨价；点击线索看证据和规则 | P0；只提示复核，不认定欺诈；数据不足不给个人习惯结论 |
| 用户纠正与归类 | “这笔是差旅，不是日常交通”；预览分类修改，记录修正原因 | P1；不改金额与原始流水字段；修正后重算报告并保留来源 |
| 月度 / 年度报告 | 固定口径统计、主要变化、待复核事项和相关交易列表 | P0；已有导出能力复用；只有部分月份数据时注明覆盖范围 |
| 预算与资金预测 | “本月餐饮控制在 1500 元”；对照用户目标及已知未来扣费，显示剩余额度 | P1；区分已发生、已授权、预计和未知，不将 AA 待收款当作已到账现金 |

数据方案：增加可重复生成的虚构历史样本，覆盖至少六个月及跨年样例，包含涨价、正常重复消费、月末扣费和非订阅消费。统计规则使用版本号及明确的最小样本要求；样本不足降级为单笔核对。所有汇总使用整数分，模型只解释工具已计算的指标。

页面方案：账单页增加紧凑问答入口；回答显示“结论 + 计算口径 + 证据交易”。异常点击后打开明细抽屉，复用现有图表、明细与导出，不添加大面积介绍板块。

### C. 智能订阅与代扣管家

| 功能 | 用户表达与智能行为 | 优先级 / 验收重点 |
| --- | --- | --- |
| 周期扣费诊断 | “哪些钱每个月自动扣”；按商户规范名、日期间隔、金额变化提取候选 | P0；展示原始扣费记录，正常分期或常去餐厅不直接认定订阅 |
| 协议核实 | 将账单线索与实际保存的模拟代扣协议关联 | P0；分别标记“疑似周期扣费”“已有协议”“已取消”；没有协议不能声称已取消成功 |
| 续费与涨价提醒 | 展示已知续费日、预计日期区间、费用上涨依据；演示时间到期生成站内提醒 | P0；预测须标“预计”，同一提醒不重复生成；当前只做站内提醒 |
| 精简订阅建议 | “哪些可以省下来”；展示周期成本、功能相近项目，询问用户是否需要保留 | P0；流水无法证明使用频率，不能自动声称“长期没用” |
| 多项取消计划 | “保留音乐，取消我选的这两项”；列表逐项勾选，展示下次扣费和取消影响 | P0；每项有授权和结果；无选中项不执行，失败项不拖累已完成记录 |
| 周期异常后续动作 | 取消后仍见扣费时生成复核线索，显示交易时间与协议生效时间 | P1；不自动认定违规、不虚构已退款或已向商户投诉 |

节省金额口径：区分“未来某个结算周期可能避免的扣费”和“已退回现金”；年费不能未经说明直接当成每月可用现金。只有成功取消、有效日期及计划周期都符合时，才纳入相应期间的预计减少金额。

取消银行代扣与退订商户服务是不同动作。当前工具只能取消已有模拟代扣协议；没有商户退订接口时，不显示“会员服务已退订”，也不推断其他付款渠道不会继续扣费。

### D. 跨场景任务规划

#### D1：本次参赛主线——支出优化计划（P0）

用户表达：**“帮我看看上个月为什么花得多，再看看下个月能不能少花 300 元。”**

1. 查询可比账单，计算主要增加项，输出证据。
2. 检查其中的周期扣费，核对协议和续费时间。
3. 列出可选择的方案及预计影响；询问必须保留的服务。
4. 用户明确选择并确认具体协议后，逐项取消模拟代扣。
5. 返回每项结果、实际仍在生效的协议和预计节省差额。

若只能找到 128 元的可减少扣费，应明确距 300 元目标还差 172 元，不擅自取消其他服务或虚构达标。根据真实查询结果选择工具；不能把演示的商户、金额和执行顺序写死在回复中。

这个最小任务限定为账单查询、订阅核实和已选协议取消，最多四个执行步骤。账单到 AA 的跳转继续提供，但不能把消费自动变成他人应付债务。

#### D2：生日资金与服务计划（P1 / 进阶）

用户表达：**“11 月 20 日是爱人生日，留出 1000 元，提前两天订花和蛋糕。”**

- 澄清生日年份、联系人、配送信息、服务选择、每项预算及总额、购买日期、取消条件。关系和日期由用户提供，不从通讯录或账单猜测。
- 先实现预算预留台账：`可用余额 = 账面余额 − 有效预留`；所有转出工具都遵循可用余额，不能只在页面显示预留数字。
- 花店和蛋糕店使用虚构商品及订单工具。只有具体商品、对象、时间窗口、价格上限、费用和授权期限都获确认，才能在约定时间自动下模拟订单。
- 价格、商品、配送对象等超出授权即暂停并请求重新确认；不能靠一句“帮我安排”获得不限范围授权。
- 预留、每个订单、支出和回执分别记录；部分完成后只释放未使用资金，不能声称已完成订单被整体回滚。取消订单及退款须有自己的状态流。

D2 依赖持久化多步计划、可用余额规则、预留账本和模拟商户工具，不能只给现有预约任务换一个名称。

### E. 智能卡片管理

| 功能 | 用户表达与智能行为 | 优先级 / 验收重点 |
| --- | --- | --- |
| 卡片状态与临时锁定 | “卡找不到了”；先列出卡片、澄清卡号尾号，解释临时锁卡与挂失区别，再按选择执行 | P1 最小闭环；默认先提出方案，不自行锁卡或挂失 |
| 解锁与交易限制 | “关闭这张卡线上支付”“找到了，帮我解锁”；明确卡片和渠道 | P1；独立确认，模拟刷卡工具必须执行这些限制，光改 UI 状态不算完成 |
| 卡片挂失 | 用户明确挂失，核对影响并通过独立的模拟强验证 | P2；挂失不同于临时冻结，不能普通解锁直接恢复；未实现验证时继续拒绝 |

### F. 智能理财助手

| 功能 | 用户表达与智能行为 | 优先级 / 验收重点 |
| --- | --- | --- |
| 需求澄清与风险测评 | “有笔钱暂时不用”；补问用途、可用日期、风险承受和流动性需求，提交问卷 | P2 第一阶段；测评由版本化规则计算，不由模型随意给等级 |
| 产品筛选、推荐与对比 | 基于虚构产品目录，对比风险、期限、赎回限制和费用，给出匹配依据 | P2 第一阶段；每项指标引用产品记录和版本；匹配不足则不推荐 |
| 模拟申购 | 用户选定产品和金额后，检查测评有效性、适当性、可用余额、起购金额和产品状态 | P2 第二阶段；模拟强验证，现金、份额、订单和回执一致更新 |
| 模拟赎回 | 用户选择持仓和份额，解释费用及到账时间，再确认 | P2 第二阶段；检查可赎份额和锁定期；未到账赎回款不可花费 |
| 到期与持仓解释 | 解释持仓变动、到期日及流动性约束 | P2；不预测保证收益，不自动换仓或自动续投 |

首个可运行理财版本使用明确的虚构净值及一种结算方式，例如“成交后下一演示工作日到账”；净值、交易日历、费用、份额精度和舍入规则需要先固定。持仓收益不能随模型回复变化。此处为模拟产品设计，不构成实际投资建议。

## 4. 所有场景共用的智能执行能力

### 4.1 受约束的任务计划

模型可提出目标分类、查询参数和待补齐项；服务端将它们映射到固定工具。首版支持有限的计划结构：

```text
目标 → 查询事实 → 澄清/选择 → 生成有版本的计划 → 授权 → 按依赖执行 → 逐步回执
```

- P0 计划只允许白名单工具和有限步骤，禁止模型自由生成 SQL、执行代码或任意工具名称。
- 状态至少包括 `draft / awaiting_input / awaiting_confirmation / running / partially_completed / completed / failed / cancelled`，有预约步骤再增加等待时间状态。
- 每一步保存输入、依赖、证据 ID、授权范围、幂等键和结果；总体完成以所有必需步骤的真实结果为准。
- 用户修改对象、金额、时间、协议或计划版本后，相关授权失效；已执行操作不能被修改草稿直接撤销。

### 4.2 授权、失败与恢复

| 操作 | 计划规则 |
| --- | --- |
| 查询、统计、推荐草稿 | 可自动执行；个人数据仍限制在当前模拟账户 |
| 小额转账、AA 建单、订阅取消 | 展示具体摘要并确认；重复调用复用原执行结果 |
| 高风险转账、挂失、申购等 | 目前继续拦截；扩展阶段须有独立模拟强验证，再决定是否执行 |
| 未来执行 | 只在已确认的对象、金额、时窗和次数内执行；到期重检条件 |
| 业务失败 | 返回明确原因，停止依赖步骤；余额不足、对象变化不能无限重试 |
| 技术中断 | 幂等键和账本状态可确认未执行时才能恢复；不凭超时猜测失败后重新扣款 |

上述级别是本原型的权限策略。模拟二次验证不等于真实身份系统；更不能把点击“我已验证”当作生产级强验证。

### 4.3 可核验解释与记忆

- 每条回答区分模型解释、规则判断、银行工具数据和用户提供信息；不能展示伪造的模型内部推理。
- 证据包含交易/协议/计划编号、时间范围和统计版本；用户可点击查看。
- 只保存用户明确确认的别名、预算及偏好；可查看、修改、删除，不推断隐私关系或永久记录未经确认的风险偏好。
- 交易备注、商户文本、产品文案属于数据，不能改变权限或发起动作。

### 4.4 成本与演示稳定性

- 沿用 DeepSeek 适配层、确定性工具和规则降级；不引入多模型投票或持续循环调用。
- 显式生成计划时调用模型；输入中的每次按键、图表切换、回执刷新均不触发模型。
- 记录模型、输入/输出 token、延迟、降级原因；金额估算依赖配置的价格，不冒充平台实际账单。
- 20 元是总预算，实际剩余额度先扣除平台已有消费。为本项目配置可调警戒线与调用上限；预算不足可继续用规则演示。
- 只缓存带账本版本的只读结果；余额、权限、写操作确认和执行前校验不得由旧缓存替代。
- 准备虚构数据快照和明确的演示时钟；重置须由用户明确操作，不能在演示中自动清空数据掩盖错误。

保持深蓝/冷蓝/金色确认的现有风格，复用紧凑列表、可缩放聊天、证据抽屉和明细弹窗。

## 8. 演示、评测与提交

建议 4 分 40 秒主视频，留下 20 秒余量：

| 时间 | 镜头 | 证明什么 |
| --- | --- | --- |
| 0:00–0:20 | 项目定位与模拟标识 | 目标和数据边界清楚 |
| 0:20–1:15 | 问“为什么花得多”，打开证据 | 解释可复算，能连接具体交易 |
| 1:15–2:25 | 核实订阅、选择取消项、确认及回执 | 跨场景规划和逐项授权 |
| 2:25–3:20 | AA 分摊与单人模拟回款 | 精确金额、建单不入账、到账才变化 |
| 3:20–4:10 | 同名或高风险请求、查看执行记录 | 不确定先澄清、越界不执行、结果可追溯 |
| 4:10–4:40 | 架构、实测结果及限制 | 实现与宣传一致 |

专项测试按场景断言最终账本和状态：正常路径、缺参/歧义、越权/提示注入、过期/重放、超时/失败、并发/恢复。评测报告单列规则模式、mock 模型与真实 DeepSeek 调用，公布实际成功率、失败样例、延迟和估算调用成本，不能把已有单元测试通过率写成真实模型任务成功率。

交付清单：系统架构图、算法说明、安全设计和权限矩阵、已知风险清单、评测证据、README 与部署材料、干净源码仓库、10 分钟以内答辩 PPT、5 分钟以内视频。是否发布仓库及具体托管位置留到形成可审查的提交版本时再决定。

## 9. 原计划中的实施起点（已实施）

先做 **F01–02：智能账单问答** 的最小纵向流程：

> 用户输入“上个月餐饮花了多少？” → 解析时间与分类 → 服务端计算 → 展示总额、期间、交易数量 → 点开相关明细。
